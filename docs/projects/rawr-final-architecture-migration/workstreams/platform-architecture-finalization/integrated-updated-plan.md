The execution-ready shape is: **keep `frozen` as the platform baseline, extract the spec-system invariants as a companion authority, harvest `_inbox/latest` for framing improvements, and use the runtime realization spec as the authority for settled runtime decisions**. That preserves the platform document as a hub without letting useful `latest` language silently promote runtime mechanics into platform ontology.

**Why This Order**

The dangerous move would still be integrating `_inbox/latest` directly into `frozen`. `_inbox/latest` has useful language and several forward-looking decisions, but it also collapses some runtime mechanics into the platform document. The updated order keeps its value while stripping away the authority leak.

The spec-system extraction remains first because it creates a neutral place for corpus law. The platform spec can then say "I am the platform hub" without carrying the whole specification governance system inline. That makes the final platform document cleaner and makes future companion specs easier to evaluate.

The harvest packet is the second safety valve. It prevents "good wording" from carrying hidden decisions. Every `_inbox/latest` idea must declare whether it is document structure, platform architecture, runtime mechanics, spec-system governance, or deferred cleanup.

The runtime boundary scrub is now sharper than in the prior plan because several old uncertainties are no longer open. `ProviderEffectPlan`, `providerFx`, `ExecutionRegistry`, `ProcessExecutionRuntime`, descriptor-first execution, and the one-terminal rule are settled by the runtime realization spec. The platform spec should cite them only as architecture-level laws or integration boundaries; it should not become the mechanics catalog.

**Low-Confidence Boundaries**

Only these should stay explicitly low-confidence for now:

- The exact hub vocabulary rule for runtime nouns: which names are allowed as boundary references and which must stay out of platform ontology.
- Whether to add one platform sentence banning Effect-prefixed semantic kinds such as `EffectService` / `EffectPlugin`, and exactly where it belongs.
- Whether `SurfaceRuntimeAccess` belongs in platform vocabulary, remains runtime-only, or needs a taxonomy correction across both docs.
- The platform/deployment external-interface lock point.
- OpenShell governance/vendor details beyond the already-locked harness/native-interior boundary.

These should not block the platform spec reframe. They belong in Chunk 6 unless earlier chunks make the answer obvious.

**Concrete End State**

You end with:

- One finalized **Platform Architecture Specification**, based on `frozen` plus selected `_inbox/latest` improvements and settled runtime-boundary decisions from the runtime realization spec.
- One standalone **RAWR Specification System** companion doc that owns cross-spec rules and extracted invariants.
- One harvest packet showing exactly what was taken from `_inbox/latest`, adapted, rejected, or deferred.
- One narrow conflict packet for residual wording/taxonomy/governance questions that should not be smuggled into the platform spec.
- Stale `main`/external/inbox copies classified as current authority, harvested provenance, or obsolete.
- A clean authority split: platform spec owns platform ontology and boundaries; runtime realization spec owns runtime mechanics; spec-system companion owns corpus governance.
