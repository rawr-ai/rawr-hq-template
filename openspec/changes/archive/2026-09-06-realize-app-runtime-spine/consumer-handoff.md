## Shared Consumer Contract

For an existing Habitat installation, the owner-local change uses native
`bunx nx migrate @habitat-ai/cli@0.6.0 --no-interactive`, then the repository's Bun
installation and any actual migrations generated by Nx. The CLI package group
supplies the exact SDK pair; do not independently choose another SDK version or
copy producer files. An absent or empty migration plan from the current 0.5.15
foundation is expected: no migration generator steps are required, but the
CLI/SDK dependencies and lockfile still upgrade. It does not mean product source
was converted. Older baselines may have real migration entries. Preserve normal
provenance checks.

Repeat the same-version native migration and frozen installation to establish no
further package, lockfile or foundation changes. A repository without Habitat may
instead enter through `bunx nx add @habitat-ai/cli@0.6.0 --no-interactive`.
Neither path authorizes product restructuring or prototype deletion.

Habitat owns generic lifecycle mechanics; Marketplace independently owns curated
content, declarative policy/evaluation inputs, and governed acceptance, release
and channel records. Semantic-ledger (D-1) and temporal-inquiry (D-2) integrations
are not in this release; each retains its independent acceptance and release gate.

The published pair supplies these boundaries, qualified by the
[release receipt](runtime-release-receipt.json) and
[implementation evidence](../../../../docs/projects/habitat-runtime-realignment/IMPLEMENTATION.md):

- Explicit public authoring faces: `@habitat-ai/sdk/service`, `service/schema`,
  `effect`, `execution`, the selected `plugins/*` face, and
  `runtime/resources`, `runtime/providers`, `runtime/providers/effect` and
  `runtime/profiles`. Managed service binding uses `sealService` and `useService`;
  consumers do not import private provisioning/compiler owners.
- `@habitat-ai/sdk/app` supplies `defineApp`, `defineProcessCatalog`,
  `defineEntrypoint` and `startApp`. One finite app catalog can contain separately
  started server and async processes. Each thin entrypoint passes its exact cold
  selection to one `startApp`; it is not a sibling-process controller.
- Launch identity is immutable `{ app, process, entrypoint, deployment, source }`.
  Same-app processes have independent leases, resources, health and stops.
  Readiness is fail-closed and process-local. Deployment derivation preserves its
  cohesive cold references; a serializable plan does not replace executable refs.
- `app@1` remains byte-identical and independently resolvable at
  `@habitat-ai/sdk/blueprints/app/blueprint.toml`. Complete `app@2` resolves at
  `@habitat-ai/sdk/blueprints/app/versions/2/blueprint.toml` without inheritance or
  fallback. Installing 0.6.0 does not select app@2 or convert app source for you.
- `runtime/harnesses` is the public companion contract; native Elysia, Inngest and
  Bun web factories have separate subpaths. Unselected optional hosts remain
  import-safe. Install a native peer only for the integration you actually use,
  at the version qualified by the released manifest.
- Native OTLP receipts establish transport, ancestry and finalization, not
  collector persistence, queryability or universally secret-free exports. Backend
  qualification, exception export policy and EVLog evaluation remain D-5. Native
  agent/OpenShell and desktop host qualification remains D-4. Their authoring and
  managed executable faces are implemented, not merely cold declarations.

The [immutable app@1 source](https://github.com/rawr-ai/rawr-hq-template/blob/f52474a7abc232d881cd1cf272f1d063a265285d/.habitat/blueprints/app/blueprint.toml)
and [complete app@2 source](https://github.com/rawr-ai/rawr-hq-template/blob/f52474a7abc232d881cd1cf272f1d063a265285d/.habitat/blueprints/app/versions/2/blueprint.toml)

## Lane Notes

### Rawr

Use the existing installation's native migration through Rawr's owner-local
OpenSpec, not `nx add` or a blanket source re-import. Preserve current corpus,
Hyperresearch and session-intelligence behavior; compare later held changes with
the actual destination before adopting them. Habitat's external-extension,
curated-plugin and development commands do not transfer Rawr domain or
Marketplace release authority. `dev stack drain --apply` requests a native merge;
it does not verify completion or perform the later forced synchronization sweep.

Return genuine service/topic and selected-runtime acceptance. D-3 workstream
adoption waits for the separate D-1 semantic-ledger release; research and session
work wait only for prerequisites they actually use. Governance references are
review-only, not executable adoption.

### Research-Service

Use the public service contract/client/router boundary and the five context lanes:
`deps`, `scope`, `config`, `invocation`, `provided`. Construction binding is distinct
from per-call context; managed clients do not grant a second runtime or provider
owner. These lanes belong to `ServiceBoundaryContext`; the disjoint
`ServiceModuleContextProjection` contains none of those lane names. Return
domain behavior, exact context/error propagation and selected provider
acquisition/release proof. Already released service law need not wait for this
runtime, and research has no blanket ledger/inquiry dependency.

### Civ7

Adopt only the public law and runtime subset your actual host supports. Service
law availability is not blocked on unrelated runtime work, but Habitat's Node/Bun
native-host qualification does not establish Civ7/V8-isolate compatibility.
Return exact-version migration, installed boundary checks and the real host's
compatibility disposition; do not import Node host plumbing to satisfy a generic
runtime checklist.

### Magic Migration

The release supports your one-app/separate-server-and-async demand through the
public app, resource/profile and native harness faces. Return built/deployed
selection, independent process identity/readiness/stop, refusal-before-mount and
native drain-before-release proof for your actual composition. Product routes,
providers and deployment wiring remain Magic-owned. Native Bun web module and
Effect routes do not imply browser execution or a full SSR framework. Keep the
MCP prototype separate while the independent companion condition is unsatisfied.

### Inngest

The release qualifies native `inngest@4.18.0` Serve/Connect. Use `plugins/async`,
`plugins/async/effect` and `runtime/harnesses/inngest`, not an `effect-inngest`
replacement runtime. Native orchestration owns retries/replay/memoization; actual
authored Effect step descriptors enter the managed boundary through
`stepEffect(context).run(descriptor)`. Ordinary orchestration stays native.
Completed memoized steps skip execution; failed or unmemoized attempts invoke
the Effect callback anew. Return your selected mode's
native retry, memoization, cancellation and shutdown/resource-retention evidence.

Server-side named `useWorkflowDispatcher` admission uses an existing required
client resource and an exact workflow subset without selecting async execution.
Its event IDs acknowledge native admission, not workflow completion. Unselected
Inngest remains optional; Cloud acceptance is distinct from local native proof.

### MCP-Companion

Task 13.6's independent ordinary-artifact condition remains unsatisfied. No MCP
authoring face or built-in MCP lifecycle is released. Re-entry needs an
independently versioned ordinary companion artifact and qualification against
the public generic harness contract, including native lifecycle/readiness and
the claimed tools/OpenAPI resource surface. A Magic vendor tarball or copied
source is not that artifact. Return a concrete artifact/acceptance proposal, not
a claim that the unavailable attachment blocks unrelated runtime adoption.

### oRPC

The release uses the official `@orpc/*@2.0.0-beta.32` family with
`effect@4.0.0-beta.101`. Ordinary synchronous/Promise operations stay native
`.handler`; Effect operations use the official implementation-owned `.effect`
bootstrap through `@habitat-ai/sdk/plugins/server/effect`. Keep one native module
realm and exact per-call context/wrap; do not add a custom runner or dispatch
through private `handlerGen`. Return declared error, defect, abort, context and
native settlement/correlation proof for your actual service/server boundary.
