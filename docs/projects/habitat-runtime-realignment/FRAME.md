# Habitat Capability Realization

Frame owner: Codex under the September 4, 2026 owner delegation.
Object: solution realignment; second-order revision of delivery and authority,
not replacement of Habitat's product purpose.
Mode: embedded-intent discovery followed by delegated design and review.
Status: accepted and reconciled after composed review; repository admission is
tracked in [WORKSTREAM.md](WORKSTREAM.md).

## Situation And Destination

This frame treats a realized capability, preserving its meaning from authoring
through operating behavior and consumer adoption, as the unit of progress.
Source modules, policy packets, receipts and task completion are evidence about
that capability, not substitutes for it. A concrete failed contract blocks the
work that requires it, not every later item in a historical queue.

The intended destination remains the full Habitat substrate: reusable semantic
authoring and governance, a complete native runtime, observability, deployment
interfaces, and independently owned consumers. The runtime is complete only
when real services and resources operate through their native hosts, with
process-local identity, failure handling, cancellation, observation and stop.
A cold plan, an empty-service fixture or an in-repository demo is not that end
state. Separate platform outcomes remain explicit even when they do not belong
to the runtime release's dependency closure.

This preparation ends before runtime implementation resumes. It must leave one
coherent target and an executable path to that destination, not pretend the
destination has already been reached.

## Why This Frame

The prior operating frame is inferred from the queue, not attributed to the
owner: seal a linear sequence while preserving each previously written
constraint, then expose runtime value. Its failed prediction was that ever more
precise packets would reduce uncertainty. Instead, optional ledger semantics
stopped generic runtime work, private file arrangements became governing law,
and historical execution instructions accumulated inside canonical specs.

The named reframing move is **double-loop change**: change the progress measure
and the authority of constraints. Dependency decomposition and relaxation of
incidental layout are consequences. Simply skipping task 6.3f would leave the
same failure mechanism intact.

Structural alternatives considered:

- Restore the older RAWR specification wholesale. Rejected: it loses accepted
  semantic clarification and useful source without proving a better target.
- Keep only a small consumer-specific runtime. Rejected: easier acceptance
  would substitute a narrower product for Habitat's reusable substrate.
- Preserve the architecture, reconcile its contradictory rules and realize
  complete outcomes by actual dependencies. Selected: it repairs the governing
  problem while preserving the original ambition and valuable implementation.

## Selection Commitments

**In:** the semantic owner model; authoring-to-runtime artifact handoffs;
process lifecycle; source and policy gaps; release and consumer acceptance;
the disposition of every inherited work obligation.

**Foreground:** meaning-preserving composition, real operating behavior,
native vendor integration, honest evidence states and a cold-startable current
target. The hardest unresolved integration boundary gets attention before more
declaration-only proof.

**Exterior:** rebuilding the entire platform from scratch; silently choosing
new product goals; authorizing a database distribution; migrating Civ7 or Magic
during preparation; general cleanup of historical branches; inventing a new
ontology pipeline or review bureaucracy as a prerequisite.

## Hard Core

1. **Meaning has an owner.** Services own domain behavior; resources declare
   capabilities; providers realize them; plugins project; apps select. Habitat,
   downstream products and Marketplace remain independent owners/repositories.
2. **Realization preserves meaning.** Definition, selection, derivation,
   compilation, provisioning, mounting and observation remain distinct phases.
   Instance and dependency-slot identity survive their handoffs.
3. **A process owns its life.** Each start owns its resources, native handles,
   identity and stop. Sibling processes cannot acquire lifecycle authority over
   each other merely by belonging to one app.
4. **Native mechanisms remain native.** Habitat coordinates Effect, oRPC,
   Inngest and native hosts; it does not reproduce their execution engines or
   move product semantics into a platform runner.
5. **Claims follow evidence.** Defined, implemented, verified, released and
   consumer-accepted are different states. A deferred integration retains its
   promised semantics and is not advertised as delivered.

## What May Change

Private source decomposition, helper names, exact DTO representation where not
publicly committed, algorithms, proof organization, phase grouping and release
ordering can change when they preserve the hard core. Versioned immutable
blueprint closures remain immutable; better policy uses complete successors.
No fixed count of private source files, changed files, evidence documents or
lockfile records is a product guarantee.

The default response to a local bug is a focused repair, not another system
reframe. A scope decision is required when the intended outcome, ownership,
external operating obligation or compatibility promise changes.

## Reframe Conditions

Reopen the frame if a real required consumer cannot be realized without ledger
merge as a generic runtime prerequisite, or if the preserved owner/lifecycle
model prevents the explicitly required callable, portability or process
isolation behavior. That requires a concrete dependency or failing scenario,
not merely an inherited task-order statement.

Degeneration trigger: if two successive implementation containers add only
policy, proof infrastructure or exceptions without reducing a named capability
gap, reassess the delivery frame before opening a third. This is an attention
trigger, not a new standing monitor or an excuse to omit necessary tests.
